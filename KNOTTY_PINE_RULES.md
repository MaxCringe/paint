# KNOTTY PINE — правила разработки

> **Главный принцип:** не ломать то, что уже работает. Улучшать игру постепенно, сохраняя возможность вернуться к проверенной версии.

Этот документ — договорённости по разработке игры **KNOTTY PINE**. Они нужны, чтобы изменения были понятными и безопасными даже для начинающего разработчика.

Стабильная точка — **конкретный коммит**, а не всегда текущая вершина `main`. После принятия владельцем нового результата можно записать здесь следующий проверенный коммит.

## Восемь правил

### 1. Только одна ветка — `main`
- Не создавать дополнительные ветки, экспериментальные ответвления и Pull Request.
- Работать непосредственно в `main`, только с согласованными изменениями.
- Для возврата к предыдущим версиям использовать историю коммитов Git; новые ветки для этого не нужны.

### 2. Одна небольшая задача — один понятный коммит
- Менять только то, о чём договорились.
- Например, при улучшении лавы не изменять заодно Фиону, лес, души и управление.
- Писать понятное сообщение коммита: что именно изменено.

### 3. Не менять работающие системы без необходимости
- Сохранять существующую механику, внешний вид и настройки, если задача их не затрагивает.
- Не переписывать крупные файлы и подсистемы ради маленького визуального эффекта.
- Если без связанных изменений не обойтись — заранее объяснить почему.

### 4. Глобальные переделки — только после согласия
- Не менять архитектуру, игровой движок, сборку, фреймворк или библиотеки по собственной инициативе.
- Не переносить и не переименовывать файлы без согласования.
- Предлагать безопасный план перед рискованной работой.

### 5. Проверять каждое изменение
- Перед коммитом проверять синтаксис, а для проекта с Vite — сборку (`npm run build`), когда инструменты доступны.
- Проверять связанные механики и внешний вид в браузере, когда есть возможность.
- Если реальный запуск или визуальная проверка недоступны, **честно это указывать**; успешный коммит не равен рабочей игре.

### 6. Обеспечивать простой откат
- Сохранять небольшие, понятные коммиты, чтобы можно было восстановить предыдущую стабильную версию.
- При ошибке сначала выяснить, что сломалось, и при необходимости откатить проблемное изменение.
- Не накапливать новые исправления поверх явно сломанной версии без согласования.

### 7. Vercel — основная площадка для проверки
- Для изменений использовать GitHub `main`; проверять результат на Vercel.
- **Cloudflare вручную не трогать**, если владелец отдельно этого не попросит.
- Помнить: если Cloudflare тоже автоматически подключён к `main`, коммиты могут запускать обновление и там. Нельзя обещать, что GitHub-коммит затронет только Vercel.

### 8. Финальное решение — за владельцем
- После каждого изменения объяснять, что изменено, и давать возможность проверить игру.
- Только после подтверждения владельцем считать новую версию стабильной.
- Если результат не понравился или работает неправильно — вернуться к предыдущей согласованной точке.

## Как работаем над каждой задачей

1. **Согласуем цель:** что меняем, а что должно остаться без изменений.
2. **Оцениваем риск:** предупреждаем о возможных последствиях до внесения изменений.
3. **Делаем минимальную правку** в `main`, без новых веток.
4. **Проверяем доступным способом:** синтаксис, сборку, сайт, игровые механики.
5. **Сообщаем результат:** ссылка на коммит, список изменений и что реально проверено.
6. **Ждём оценки:** владелец принимает результат или просит откат.

## Как сообщать о результатах

Нужно отдельно различать три состояния:

- **Сохранено в GitHub:** коммит существует и доступен в `main`.
- **Собрано / опубликовано:** есть подтверждение успешной сборки и публикации на Vercel.
- **Проверено в игре:** запуск и конкретные механики действительно проверены.

Никогда не называть работу полностью завершённой, если проверена только запись в GitHub.
